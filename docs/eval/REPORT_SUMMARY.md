# 检索质量评估汇报

> 数据来源：`docs/eval/` 端到端评测（28 条固定查询 × LLM judge × 冻结快照）
> 快照：13,479 个知识单元 ｜ Judge：glm-5.1 ｜ 评测日期：2026-07-02

---

## 一句话结论

**核心检索场景（实体查询）达到产品可用水平，边缘场景（多实体对比 / 无实体主题）表现偏低，但每个低分都能定位到明确的、可解释的根因。**

这不是"系统不行"，而是"系统在主要矛盾上够用，次要矛盾已知且有边界"。

---

## 核心场景：可用 ✅

Agent 最高频的调用是"查某实体的概况/别名/带条件过滤"。这类场景的表现：

| 场景 | nDCG@10 | MRR@10 | P@5 | 解读 |
|------|---------|--------|-----|------|
| 单实体概况（8条） | **0.870** | 1.000 | 1.000 | 第一条命中，top-5 全相关 |
| 别名解析（4条） | **0.756** | 1.000 | 0.85 | BYD→比亚迪、CATL→宁德时代，跨语言解析准 |
| 带过滤查询（3条） | **0.701** | — | — | 时间/事件类型过滤生效 |
| 意图感知（2条） | **0.924** | 1.000 | 1.000 | 不同意图返回不同结果 |

**关键信号**：单实体场景 **MRR=1.0、P@5=1.0**——意味着 Agent 调用时，返回的第一个结果就是对的，前 5 条全部相关。这是"工具可直接用"的水平。

代表性查询：
```
"宁德时代"     → nDCG 0.888，top-1 命中，90 条召回全相关
"CATL"        → nDCG 1.000，英文别名正确解析到宁德时代
"恒大" + 债务违约 → 过滤生效，返回重组/诉讼类 KU
```

## 边缘场景：有已知边界 ⚠️

| 场景 | nDCG@10 | 根因 | 性质 |
|------|---------|------|------|
| 多实体对比（4条） | **0.252** | 见下文归因 | 数据结构约束 |
| 无实体主题（6条） | **0.340** | 见下文归因 | 分词 + 召回限制 |

这两类不是"算法差"，而是有明确的、第一性原理可解释的原因。

### 边缘场景①：多实体对比为什么偏低

**根因：statement-level 语料里，两公司同时出现在一条陈述里是稀有事件。**

实测全库共现数量：
```
宁德时代 + 比亚迪   → 2 条共现 / 全库
华为 + 中芯国际    → 0 条共现 / 全库
小米 + 腾讯       → 4 条共现 / 全库
```

这不是召回算法的问题——**库里本来就没有足够的"两家同框"内容**。每个知识单元是"来源中的一次陈述"，天然只围绕一个主体。

**已做的优化**：改"召回后用词表加分"为"召回时分实体配额 + 共现优先 + 轮流平衡"。优化后：
- Q20（宁德 vs 比亚迪）：nDCG 0.359 → **0.492**（+37%），MRR 提升至 1.0
- Q22（小米 vs 腾讯）：nDCG 0.462 → **0.516**（+12%）

**坦诚的边界**：即便优化后，comparative 的天花板受限于"语料里两实体共现稀少"这个结构性约束。检索层能保证两家都被公平召回（balance 已实现），但无法判断"哪条更适合对比"——因为对比维度（财报？技术？市占率？）不在查询输入里，这是 Agent 的职责。

### 边缘场景②：无实体主题检索为什么偏低

**根因：中文分词 + BM25 词面召回的固有局限。**

- **零召回（zero-hit）**：Q19"光刻"返回 0 条。FTS5 分词后"光刻"未被切出可匹配 token，词面召回彻底失败。
- **低相关密度**：Q17"供应链金融"召回 100 条但只有 4 条相关——BM25 把词面相近但主题不符的噪声都召回了。
- **但热门主题表现好**：Q14"半导体"nDCG=0.766、Q15"大模型"nDCG=0.891——高频主题词召回准。低频/专业术语是短板。

**这是 BM25 词面匹配的本质局限**，不是配置问题。解法是补 dense（向量语义召回），项目已有 FAISS 索引基础设施。

## 可归因：每个低分都能说清"为什么"

| 查询 | 分数 | 归因 | 类型 |
|------|------|------|------|
| Q19 光刻 | 0.000 | BM25 分词零召回 | 分词局限 |
| Q21 华为vs中芯 | 0.000 | 全库 0 条共现 + 中芯国际 KU 仅 18 条 | 语料约束 |
| Q23 伊朗vs以色列 | 0.000 | 国家实体不在实体库，走 BM25 fallback | 实体类型覆盖 |
| Q17 供应链金融 | 0.000 | BM25 召回噪声，相关仅 4/100 | 召回精度 |
| Q16 量化交易 | 0.055 | 同上，相关仅 14/100 | 召回精度 |

**没有一个低分是"莫名其妙差"**。每个都能定位到：要么是语料结构性约束（共现稀少），要么是已知技术局限（中文分词、实体类型覆盖），要么是可修的召回问题（dense 补充）。

## 评估体系本身的成熟度

不只是"能跑出分数"，而是**工程化的质量保障机制**：

| 维度 | 实现 |
|------|------|
| **可复现** | 固定 28 条 eval set + 冻结 DB 快照，每次评测条件一致 |
| **Ground truth** | LLM judge（glm-5.1）3 级标注，缓存按 (query, ku, model) 增量 |
| **指标严谨** | TREC 池化判定——Recall 分母用判定池相关总数，规避"top-k命中/top-k相关"的同义反复 |
| **回归门禁** | 由独立的 EDD 体系承担（`scripts/eval_run.py` + `eval_guard.py`），与本质量度量体系分工（见下注） |
| **可归因** | 按查询类别分组 + per-query 明细，低分能定位到具体查询和原因 |

这套机制保证：**任何代码改动的影响都能被量化、可追溯**。

> **关于回归门禁的诚实说明**：项目存在两套分工不同的评估体系——
> 本文件（`docs/eval/`）负责**度量绝对检索质量**（全库 13479 KU 冻结快照 + LLM judge + TREC 池化指标），本身**不产出门禁判定**；
> 回归检测由 `scripts/eval_run.py` + `eval_guard.py` 承担（在 80 KU 的 fixture 子集上重跑 golden 集，对比 `eval/baseline.json` 钉死的基线，超标非零退出）。
> 该门禁在 `.zcode/rules/retrieval-code.md` 中被规定为"修改检索代码后必须运行"，但**目前为人工触发，尚未接入 CI/pre-commit 自动执行**。
> 注意 fixture 是 golden 集子集、候选池被裁剪，故其 Recall@5≈1.000 是结构性假象，仅用于回归检测，不代表真实召回水平。
