一、项目定位 WHY

定位声明与边界

面向金融场景的知识检索 CLI 工具。将原始新闻消息加工为可检索、可溯源、可组合的知识层，供 Claude Code 等 agent 以 knowledge-cli 调用。

属于本项目（检索底座）
  • 原始消息标准化
  • 通用知识单元抽取（LLM tool-use）
  • 实体归一化 + 事件归并
  • 图谱构建与 GraphRAG 检索
  • 多索引建库（FTS5 / FAISS / Neo4j）
  • 面向 agent 的 CLI 检索接口，结构化参数入 JSON 出
不属于本项目（调用方负责）
  • LLM 意图解析（调用方直接传入 StructuredQuery）
  • 风险分析、时间线分析、主题研究等上层能力
  • 自然语言交互 / API 服务层
  • 报告生成、可视化

离线知识化流程详细说明 9 步

run_continuous() 负责把原始文档推进到可检索状态，以下为标准流程：

步骤职责设计约束
1. 接入原始消息接入增量批处理，按 doc_id 去重
2. 标准化文档标准化为 RawDocumentcontent 必须保留完整正文，不能只是摘要
3. 抽取LLM tool-use 抽取 KnowledgeUnitfail-fast：未配置或调用失败直接报错，禁止静默回退
4. 实体归一实体标准化与保守归一稳定标识优先；不确定时暂不合并
5. 时间验证验证 LLM 输出的 event_time 格式和合理性LLM 原生解析 ISO 8601，后端只做格式/合理性验证
6. 去重 + 冲突保留冲突信息发现矛盾时必须保留，不得静默覆盖
7. 事件归并保守规则生成 EventCluster宁可多簇，不误合并
8. 图谱更新同步 Entity + EventCluster 到 Neo4j所有节点/边必须可溯源到底层 KU
9. 索引构建FTS5 + FAISS 索引增量更新，处理失败不影响已持久化的 KU
在线检索流程详细说明 5 步

run_pipeline(structured_query=..., graph_enabled=True) 统一检索入口。调用方传入 StructuredQuery，不再内嵌 LLM 意图解析。

步骤职责输出
1. 实体解析查询 entity 名称 → 标准 entity_identity_ids 列表
2. 多路径召回Entity-ID / Dense / BM25 三路召回候选 KU 池
3. Intent 感知评分分层加权 + ScoringProfile排序列表
4. 图谱增强Neo4j related-event + co-involvement扩展 entity / cluster
5. PipelineResult类型化 JSON 输出knowledge_units + entities + event_clusters + graph

三、核心数据契约 CONTRACT

RawDocument — 原始输入文档 Stable

尚未知识化的输入文档。content 必须保留完整正文（用于后续证据切片），不能只保留摘要。

字段类型必填说明

source_typestrYnews / announcement / filing / research / brief
titlestrY文档标题
contentstrY清洗后完整正文
source_namestrY来源名称
published_atdatetimeY发布时间（与 ingested_at 分离）
urlstr | NoneN原始链接
languagestrY语言代码，默认 zh
marketstr | NoneN市场 CN / HK / US
tickerslist[str]N显式提及的证券代码
ingested_atdatetimeY系统接收时间
设计约束
  • published_at 与 ingested_at 必须分离记录
  • raw_metadata 允许保留原始元数据，但不得替代标准字段
KnowledgeUnit — 最小可检索证据单元 Core

主键语义：来源中的一次陈述，不是"事实/事件本体"。必须可溯源、保留冲突。每条 KU 对应原始文档中的一段独立陈述。

字段类型说明
ku_idstrstatement-level 主键
unit_kind"event" | "fact"单元大类
unit_typestr (enum 28种)标准化类型：earnings_release / executive_change / ...
summarystr标准化、可检索摘要
entitieslist[EntityRef]涉及实体：mention + entity_id + role
sourceSourceRef来源定位：doc_id + source_name + url
evidencelist[EvidenceSpan]原文证据片段（至少 1 条，禁止只有抽象总结）
timeTimeRefevent_time / published_at / extracted_at
confidencefloat 0-1抽取置信度
relation_hintslist[RelationHint]潜在关系线索：subject / object / relation_type
cluster_idstr | None归并后的事件簇 ID
conflict_status"none" | "possible" | "confirmed"冲突标记
status"active" | "superseded"证据生命周期状态
设计理念
  • statement-level 入库：一条 KU = 一次来源陈述，不是一篇文章
  • 证据优先，结论后置：任意结论都必须可回溯到 KU
  • 必须保留冲突：发现矛盾信息时不得静默覆盖
  • 不过早归并：抽取阶段不做别名归并（单篇新闻没有全局视角）
  • event_time ≠ published_at：事件发生时间 vs 报道发布时间必须分离

Entity — 标准实体对象 Core

图谱与检索的标准实体。第一版仅支持 5 种主实体类型：Company / Organization / Person / Product / Asset。行业、主题、地区、概念板块先作为标签或属性。

字段类型说明
entity_idstr标准实体主键
entity_type"Company"|"Organization"|"Person"|"Product"|"Asset"实体类型（仅 5 种枚举）
canonical_namestr标准名称

identifiersdict[str, str]稳定标识（证券代码、注册号等）
descriptionstr | None实体简述
tagslist[str]行业/主题/地区标签
source_ku_idslist[str]支撑该实体建档的知识单元
实体对齐策略（保守）
  • 优先级 1：稳定标识一致（证券代码、工商注册号）→ 直接归一
  • 优先级 2：无稳定标识时，canonical_name + alias + context 保守匹配
  • 优先级 3：匹配不确定 → 暂不合并，不生成高风险误归一
归一化覆盖场景
场景类型示例期望结果
跨语言别名BYD → 比亚迪合并
跨语言别名IMF → 国际货币基金组织合并

复合后缀阿里巴巴集团控股有限公司 → 阿里巴巴合并

EventCluster — 保守归并的事件视图 Core

多个 KnowledgeUnit 在保守规则下归并后的事件视图。为图谱和检索提供更稳定的事件级节点。

字段类型说明
cluster_idstr事件簇主键
cluster_typestr标准化事件类型
title / summarystr事件簇标题与摘要
entity_idslist[str]关联实体 ID 列表
primary_entity_idstr | None主实体
time_anchor / time_rangedatetime | dict主时间锚点 + 起止范围
member_ku_idslist[str]成员 KnowledgeUnit 列表
source_doc_idslist[str]派生来源文档
conflict_status"none"|"possible"|"confirmed"簇层冲突状态
cluster_confidencefloat 0-1归并置信度
归并条件（必须同时满足）
  • 主实体集合高度重合或可明确映射
  • unit_type 一致
  • 时间窗口足够接近
  • summary 语义相似度超过阈值
  • 不存在明显互斥陈述
默认不自动合并的情况
  • 同一主体但不同事件阶段（如"宣布收购"和"收购完成"）
  • 同一主题下的连续多次公告
  • 信息互相矛盾但尚未判明来源优先级
  • 仅依赖模糊名称匹配得出的疑似同事件

四、知识抽取设计 EXTRACT

LLM 抽取模式 — Tool-Use (Function Calling) P0

使用 Claude 的 tool-use 模式进行结构化抽取，输出为 JSON schema 约束的结构化数据，不是纯文本补全。

7 项 Prompt 设计原则
#原则要点
1Schema 优先于 prompt 文本能用 JSON schema 的 enum/description/pattern 约束的，不要只在 prompt 里描述。当前 unit_type、entity_type、relation_type、event_time_resolution、time_grain 均已注入 schema enum 约束。Schema 是硬约束，prompt 是软引导。
2正反例优先于抽象规则每个边界 case 给 1 正 + 1 反例。当前已为时间解析（6 正例 + 4 反例）、relation_hints（2 正例 + 1 反例）、unit_type（4 正例）补充了具体示例。
3显式优先级声明规则冲突时必须写明谁优先。当前优先级：准确性 > 召回率（宁缺毋滥）> 具体具名实体 > 抽象概念 > 有时间锚点的动态陈述 > 静态背景描述。
4输入首尾效应Prompt 结构重排为：published_at 锚点（顶部）→ 正文（核心输入）→ 文档元信息（底部）。正文不再被元信息夹在中间。
5可验证的自洽检查输出前必须验证：① relation_hint 的 subject/object_mention 在 entities 列表中精确出现 ② evidence.text 是正文原文片段（逐字匹配）③ unit_type 是枚举值之一。不使用主观判断。
6Prompt 只做感知抽取只负责识别提取；消歧/归并/冲突裁决交给后处理。不在抽取阶段要求模型做别名归并。
7不用 XML 标签tool-use 模式下结构化输出已天然隔离，XML 标签是冗余的。需要推理时用 Claude extended thinking。
Schema 驱动的硬约束（v2 新增）

提取工具的 JSON schema 通过 _build_extraction_tool_schema() 动态构建，注入以下 enum 约束：

字段Schema 约束效果
unit_typeenum: 28 种 UnitType 枚举值LLM 只能输出合法类型，不再自由发挥
entity_typeenum: Company / Organization / Person / Product限制实体类型范围
relation_typeenum: 合作/投资/并购/竞争 等 20 种关系类型标准化
event_time_resolutionenum: explicit / contextual / unresolved标记时间解析来源
time_grainenum: day / month / quarter / year标记时间粒度
stock_price_change 抽取约束（v2 新增）
  • 纯粹的股价涨跌数字不单独提取为 KU（如"比亚迪涨了3%"、"收盘跌2.1%"）
  • 只有当陈述包含因果归因时才提取（如"因...""受...影响""得益于""推动""带动"）
  • 正例："比亚迪涨停，因Q3净利超预期" → stock_price_change
  • 反例："比亚迪涨了3%" → 不提取
Fail-Fast 策略
  • LLM 未配置 → 直接报错
  • LLM 调用失败 → 直接报错，不静默回退启发式
  • 返回不满足契约 → 报错并记录处理失败
  • 开发阶段禁止"未配置/失败后自动回退"这类静默降级
实体上下文注入 — 辅助 LLM 标准化命名 Enhancement

问题：同一实体在不同文档中被 LLM 用不同名称识别（如"小米集团"/"小米"/"小米科技"），增加消歧负担。

方案：抽取时注入与当前文档相关的已知实体列表，帮助 LLM 使用标准名称。

匹配评分规则
匹配类型分数示例
canonical name 精确匹配10.0"小米集团" 出现在正文中
identifier 匹配（如 ticker）8.0 / 个"1810.HK" 出现在正文中
alias 匹配5.0 / 个"小米" 别名命中
设计约束
  • Token 预算控制：最多 50 个实体，约 2000 tokens
  • 注入的实体列表是辅助信号，不强制 LLM 使用标准名称
  • 不在 prompt 中要求模型"将别名统一归并为主称"——这和后处理消歧逻辑冲突
时间解析 — LLM 原生解析 + 后验证（v2 重大变更） Redesign

v1 → v2 核心变更：时间解析从"Python 后处理解析中文表达式"改为"LLM 在抽取阶段直接输出 ISO 8601 绝对时间"。TimeNormalizer 从解析器降级为验证器，只检查格式、合理性和时区。

LLM 时间解析规范（写入了 SYSTEM_PROMPT）
优先级原文类型解析规则resolutiongrain
1明确日期（"4月3日"、"2025年Q1"）直接转为 ISO 8601explicitday / quarter
2相对时间（"昨天"、"上周五"、"3天前"）基于 published_at 推算绝对日期contextualday
3模糊时间（"近期"、"本月初"、"Q1"）基于 published_at 取最合理估计contextualday / month / quarter / year
4无时间表达event_time = published_at（报道行为即事件）contextualday

TimeNormalizer 职责变更
  • v1：解析中文时间表达式（昨天、上周三、近日...）→ 绝对时间。380+ 行正则匹配代码。
  • v2：只验证 LLM 输出。检查 ISO 8601 格式、日期合理性（不超过 published_at 未来 1 天）、时区。~100 行代码。
  • 收益：LLM 拥有完整上下文（全文 + published_at），解析质量高于 post-hoc 正则。消除了 v1 中 ~380 行的维护负担。
时间解析质量监控

每次抽取后自动记录统计：resolved 比例、resolution 分布。resolved < 50% 时发出 WARNING。

用户测试数据（2026-05-20）：event_time 缺失率从 54% 降至 25%。

冲突检测 — 多源冲突保留

多来源报道同一事件时，可能存在时间、金额、参与者方面的冲突。系统必须检测并保留这些冲突信息，不得静默覆盖。

冲突类型检测逻辑标记
TIME_MISMATCH不同来源对同一事件的 event_time 不一致仅比较显式 event_time，不比较 published_at
AMOUNT_MISMATCH金额数值不一致（支持"亿元""万美元""港元"）从中文文本提取金额后比较
PARTICIPANT_MISMATCH参与者信息矛盾补充性提及不视为冲突；只有矛盾信息才标记
设计约束
  • 仅比较显式 event_time——differing published_at without explicit event dates 不产生冲突
  • 补充性参与者提及（additive）不视为冲突，只有矛盾性差异才标记
  • adjacent-day explicit event-date disagreements 标记为 possible，不静默 flatten
  • LLM 原生解析后 event_time 为绝对时间，冲突检测直接比较 datetime 值，不再需要处理中文表达式

五、检索系统设计 RETRIEVAL

多路径召回 — 三路检索策略 P0
路径适用场景核心机制优先级
Path A: Entity-ID 实体查询（明确 entity name） 按 entity_ids JSON 列直接查询，通过 canonical_name + aliases + identifiers 匹配 Primary
Path B: Dense 中文/主题查询 FAISS embedding 向量检索。LLM 归一化已在索引阶段桥接词汇差异，query-time 语义匹配作为补充。 Secondary
Path C: BM25/FTS5 Entity-ID 失败时的兜底 FTS5 全文检索 + jieba 中文分词。构建更广的 BM25 query 作为 fallback。 Fallback
为何保留 Dense 检索

分析曾发现 BM25 + 结构化打分已覆盖绝大多数场景（fusion score ~0.016 被 entity bonus 0.2 + event_type bonus 0.1 淹没），但 Vector Index 仍作为辅助路径保留，用于 broad_topic 和 entity_only 等文本匹配困难的 query type。

七、图谱设计 GRAPH

双核心建模 — Entity + EventCluster P0

图谱是 P0 正式产物，不是后续可选增强项。采用双核心建模：

节点类型
节点职责图谱角色
Entity承载稳定对象（公司、人物等）第一版主检索节点
EventCluster承载聚合后的事件视图连接实体的中间节点

KnowledgeUnit 作为证据层存在，不作为第一版主图检索节点。图谱负责结构和连接，不替代证据层。

边语义
方向语义示例
Entity → EventCluster参与、触发、涉及"小米集团" → [Q1 财报发布]
EventCluster → Entity影响、作用于[Q1 财报发布] → "小米集团"
Entity → Entity控制、持股、供应、合作"腾讯" → "京东" (持股)
EventCluster → EventCluster时间先后、因果、演进[宣布收购] → [收购完成]
溯源约束
  • 所有图节点和边都必须可回溯到底层 KnowledgeUnit
  • GraphRAG 检索必须建立在证据层可验证前提下
  • 图谱更新保留溯源信息（source_ku_ids / provenance）
GraphRAG — 图增强检索 P0

图谱增强作为检索管线的第 4 步，在 BM25 主检索之后执行。

Graph Action路径用途
Related-Event 检索Entity → EventCluster查找与某实体相关的所有事件簇
Co-involvement 扩展Entity → EventCluster → Entity通过共同参与的事件发现关联实体
Fail-Open 设计
  • Neo4j 不可用/查询失败 → 不阻断主检索路径
  • 检索继续返回 BM25 知识结果
  • 图谱错误记录在 errors 字段中
  • API 返回 ok=true（非阻断错误不影响成功判定）
PipelineResult 图谱输出契约
  • graph.graph_enabled — 是否启用图谱
  • graph.graph_used — 图谱是否实际参与
  • graph.nodes / edges / paths — 形式化图结果集
  • graph.candidate_count / expanded_cluster_count / expanded_entity_count — 扩展统计
  • graph.hit_reasons — 每个结果被图谱命中的原因

九、关键设计决策 DECISIONS

保守归并 > 激进归并
实体归一化和事件归并都偏保守。宁可多簇/多实体，不误合并。稳定标识（证券代码、注册号）优先直接归一；名称模糊匹配仅作辅助；不确定时暂不合并。
Tradeoff: 召回率可能略低（同一实体的不同表述可能被拆分），但 Precision 得到严格保障。当前实体解析 P=1.0。
Fail-Fast 抽取 > 静默降级
KnowledgeUnit 抽取默认 fail-fast。LLM 未配置、调用失败或返回不满足契约时直接报错，不静默回退到启发式。开发阶段禁止"未配置/失败后自动回退"。
Tradeoff: 系统在没有 LLM 时完全不可用（不能 fallback），但这避免了"静默降级导致数据质量不可控"的更大风险。
LLM 原生时间解析 > Python 后处理（v2 变更）
v1 使用 TimeNormalizer（380+ 行正则匹配）在抽取后解析中文时间表达式。v2 改为让 LLM 在抽取时直接输出 ISO 8601 绝对时间，TimeNormalizer 降级为验证器（~100 行）。LLM 拥有完整上下文（全文 + published_at），解析质量高于 post-hoc 正则。
Tradeoff: 如果 LLM 输出的时间格式不正确，后验证器会标记 validation_error 但不尝试重新解析。依赖 LLM 遵循时间解析规范。新增 time_grain 字段（day/month/quarter/year）记录时间粒度。向后兼容通过 _LEGACY_RESOLUTION_MAP 映射旧 resolution 值。
Schema 硬约束 > Prompt 软引导（v2 强化）
v2 将 unit_type、entity_type、relation_type、event_time_resolution、time_grain 全部注入 JSON schema enum。LLM 填参数时优先参考 schema 定义（硬约束），prompt 文本（软引导）只用于传达判断逻辑。消除了"prompt 里写只能从列表选择但 schema type:string 无约束"的反模式。
Tradeoff: enum 变更需要同时更新 UnitType 枚举和 schema 构建逻辑。但消除了 LLM 输出不在枚举范围内的后处理 normalization 负担。
Prompt 只做感知，不做认知
LLM 抽取 prompt 只负责识别和提取（感知）。实体消歧、冲突裁决、事件归并等认知任务交给后处理模块。抽取阶段没有全局视角，强行做认知任务会引入不可调试的冲突。
Tradeoff: 单篇抽取可能产出不一致的实体命名，但通过实体上下文注入 + 后处理消歧可以修正。代价是后处理链路较长。
图谱默认开启 + Fail-Open 读
图谱是 P0 正式产物，主线默认开启。读路径（GraphRAG）fail-open：Neo4j 不可用时不阻断主检索。写路径（图谱同步）失败可重试。graph_enabled=False 仅用于测试/调试。
Tradeoff: 生产环境需要 Neo4j 可用，但检索不依赖图谱——BM25 结果仍然有效。图谱增强是增量价值，不是基础前提。
LLM 意图解析已外移
LLM 意图解析从检索服务中分离。调用方（agent）直接传入 StructuredQuery 参数。检索服务不再内部调用 LLM，减少延迟和成本。
Tradeoff: 调用方需要自行构造结构化查询，但获得了更大的灵活性。IntentType 枚举保留供检索侧路由和评分使用。
Statement-Level 入库（非文档级）
一条 KnowledgeUnit = 来源中的一次陈述，不是一篇文章。粒度细化到陈述级，使得证据可精确溯源、冲突可精确标记、归并可精确匹配。
Tradeoff: KU 数量远多于文档数（80 文档 → 528 KU），存储和检索成本更高，但换来了精确的证据粒度。
Legacy 隔离 — 不回头
IntelligenceParticle、RiskReport、旧风险图查询语义已全部弃用。Skill/API/Session 模块已删除。新功能不得以旧风险模型为核心扩展。不再为旧消费链路维持兼容。
Tradeoff: 完全不向后兼容，但消除了技术债的持续积累。迁移后的代码库更清晰、可维护性更强。
