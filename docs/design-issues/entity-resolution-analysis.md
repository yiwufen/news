# 实体解析（Entity Resolution）算法分析报告

> **状态**：待架构评审
> **日期**：2026-05-10
> **涉及代码**：`src/entities.py`、`src/entity_context_filter.py`、`src/pipeline/continuous.py`
> **目标读者**：架构部门

---

## 1. 背景

实体解析是知识 pipeline 的核心环节：LLM 从新闻文档中抽取出 entity mention 后，需要将同一真实对象的不同表述（如"腾讯"、"腾讯控股"、"Tencent"）归并到同一个 `Entity` 记录上。归并质量直接影响下游检索、图谱、事件聚类的正确性。

当前系统采用**增量贪心匹配**策略：每处理一个 mention，遍历已有实体库，找到第一个满足条件的实体即合并；若找不到，创建新实体。

本报告对当前算法进行系统性审查，分析其结构性缺陷，评估"定期聚类"替代方案的可行性，并给出务实的改进建议。

---

## 2. 当前实现概述

### 2.1 核心流程

```
文档 → LLM 抽取 → KnowledgeUnit (含 entity mention)
                                  ↓
                   EntityResolver.resolve_units()
                                  ↓
                   对每个 mention 调用 _find_match()
                                  ↓
              ┌─ 匹配成功 → 合并到已有 Entity（追加 alias、source_ku_ids）
              └─ 匹配失败 → 创建新 Entity
```

### 2.2 匹配逻辑（`_find_match`，按优先级）

| 层级 | 条件 | 说明 |
|------|------|------|
| 1 | `identifiers` 字段精确匹配 | 如股票代码、ISIN 完全一致 |
| 2 | `normalize_entity_name(mention) == normalize_entity_name(entity.canonical_name)` | 去除公司后缀后精确比较 |
| 3 | mention 与 entity 任一 alias 的 normalized name 精确匹配 | 同上，但比较对象是别名 |
| 4 | `SequenceMatcher.ratio() >= 0.95` 且 `entity_type` 相同 | LCS 模糊匹配 + 类型硬约束 |

### 2.3 名称标准化（`normalize_entity_name`）

1. 去除标点和空白（Unicode category P/Z）
2. 转小写
3. 循环剥离公司后缀（"股份有限公司"、"有限公司"、"Ltd"、"Corp" 等 25 个后缀），直到无法再剥离

### 2.4 查询路径（`EntityRepository.find_by_names`）

独立于合并路径，有三层匹配：
1. 标准名称/别名匹配（同合并路径的 layer 1-3）
2. 跨语言别名字典（`_CROSS_LINGUAL_ALIASES`，如 byd → 比亚迪，硬编码 30+ 条目）
3. identifier 反查

## 3. 识别出的具体问题

### 问题一：跨语言别名不参与合并流程

**现象**：`_CROSS_LINGUAL_ALIASES` 字典仅在 `EntityRepository.find_by_names()`（查询时）使用，`EntityResolver._find_match()`（合并时）完全不调用。

**后果**：如果 LLM 从文档中抽取出 mention "BYD"，合并流程无法将其关联到已有实体"比亚迪"，会创建一个独立实体"BYD"。随后查询"比亚迪"时，两条路径查到的是不同实体，图谱中出现分裂。

**影响范围**：所有英文/拼音别名出现在 mention 中的场景。

---

### 问题二：实体类型推断不稳定导致同类实体被拆分

**现象**：`_infer_entity_type(mention)` 对每个 mention 单独推断类型，且 `_find_match` 的 layer 4 要求 `entity_type == inferred_type` 作为硬约束。

同一实体的不同 mention 可能推断出不同类型：

| mention | 推断规则 | 推断结果 |
|---------|---------|---------|
| "小米" | `re.fullmatch(r"[一-鿿]{2,3}")` | **Person** |
| "小米集团" | 匹配"集团"后缀 | **Company** |

**后果**：两个 mention 都 normalize 为"小米"，但 layer 4 因类型不同被拒绝。系统创建两个实体，查询时结果分裂。

**影响范围**：所有 2-3 字中文名 + 带后缀变体的组合（如"百度"/"百度公司"、"华为"/"华为技术"）。

---

### 问题三：全量线性扫描无索引

**现象**：`_find_match` 对每个 mention 遍历 `entities_cache` 中的所有实体（`for entity in entities_cache.values()`），无任何索引或预筛选。

**复杂度**：M 个 mention × E 个实体 × SequenceMatcher O(L²)（L 为名称长度）。

**现状**：实体量级较小（估计 < 1000），性能尚可接受。但随数据增长，该路径将成为 pipeline 瓶颈。

**影响范围**：批量处理大量文档时的延迟。

---

### 问题四：SequenceMatcher 0.95 阈值对短中文名过于严格

**现象**：`SequenceMatcher.ratio()` 基于最长公共子序列（LCS），对短字符串的插入/追加极敏感。

| A | B | ratio | 匹配？ |
|---|---|-------|--------|
| 腾讯 | 腾讯控 | 0.80 | ✗ |
| 百度 | 百度集 | 0.80 | ✗ |
| 字节跳动 | 字节跳科技 | 0.875 | ✗ |
| 阿里巴巴 | 阿里巴巴集 | 0.95 | ✓ |

**根本原因**：名称标准化（layer 2）依赖后缀剥离，但"控股"、"科技"、"电子"等常见公司名成分不在后缀列表中，导致 normalized name 仍然不同。

**影响范围**：名称含非标准后缀的公司实体。

---

### 问题五：别名列表无限增长

**现象**：每次 mention 匹配到已有实体，都会追加 alias（`entity.aliases.append(entity_ref.mention)`），仅做 `not in` 检查，无去重（normalized 级别）、无上限。

**后果**：
- 同一实体的 aliases 可能包含"腾讯"、"腾讯控股"、"腾讯控股有限公司"、"腾讯公司"等高度重叠条目
- 长期运行后 aliases 膨胀到数十个，占用存储和 prompt token

**影响范围**：高频出现的热门实体（如大型上市公司）。

---

### 问题六：贪婪后缀剥离可能过度归一化

**现象**：`normalize_entity_name` 用 `while changed` 循环反复剥离后缀。虽然长后缀排在前（如"股份有限公司"先于"有限公司"），但循环机制仍存在风险：

| 输入 | 剥离过程 | 结果 |
|------|---------|------|
| "控股有限公司" | → "控股"（剥离"有限公司"）→ ""（剥离"控股"） | **空字符串** |
| "美的集团" | → "美的" | 与"美的置业"（→"美的置业"）不冲突，但若存在另一实体"美的投资"（→"美的"）则误合并 |

**后果**：过度归一化导致不同实体的 normalized name 碰撞，产生误合并。

**影响范围**：名称含多个可剥离后缀成分的实体。

## 4. 底层原因分析

上述六个问题并非独立缺陷，而是三个架构层面设计决策的表象：

### 根因一：用逐 mention 贪心匹配代替实体聚类

实体合并本质上是聚类问题（将指向同一真实对象的 mention 归为一组），但当前实现将其简化为单次匹配——对每个 mention，找到第一个"够像"的实体即合并，不再回头。

**由此产生的问题**：
- 先到先得：第一个匹配的实体"吸收"后续 mention，即使后来有更好的匹配也无法纠正
- 没有全局视角：无法发现"两个已有实体其实是同一个"的情况
- 不可逆：一旦合并，没有拆分机制；错误合并污染 aliases 和 identifiers，影响后续所有匹配

**问题 1、2、5 的直接根源**都可追溯到这一设计。

### 根因二：查询路径和合并路径是两套独立逻辑

```
EntityRepository.find_by_names()  ← 查询时：跨语言别名 + identifier 反查 + 3 层匹配
EntityResolver._find_match()      ← 合并时：仅 normalized name + SequenceMatcher
```

两条路径各维护一套匹配逻辑，共享的只有 `normalize_entity_name` 和 `entity_matches_query_name` 辅助函数。跨语言别名仅添加到查询路径是典型的维护遗漏。

**问题 1 的直接根源**。

### 根因三：实体类型绑定在 mention 上，而非 entity 上

`_infer_entity_type` 对每个 mention 单独推断类型，推断结果仅基于字符串表面特征（长度、后缀、大小写模式），不参考已有的实体上下文。`_find_match` 将类型不一致作为**硬拒绝条件**，而非置信度降权信号。

**问题 2 的直接根源**。

### 根因之间的关系

```
根因一（贪心匹配）         → 问题 1/2/5：漏合并、误合并、不可纠正
根因二（两套匹配逻辑）     → 问题 1  ：跨语言信号在合并时丢失
根因三（类型绑定在 mention）→ 问题 2  ：同实体不同表述被硬拒绝
```

## 5. 替代方案评估：定期聚类

一个自然的改进方向是将贪心匹配替换为**定期聚类**：先收集所有 mention，再通过聚类算法将它们归并为实体。以下评估该方案在当前系统约束下的可行性。

### 5.1 与 pipeline 架构的冲突

当前 pipeline 是同步逐文档处理的：

```
文档 N → LLM 抽取 → 实体解析(即时) → 事件聚类 → 图同步
         ↑ 需要实体上下文注入 prompt      ↑ 需要 entity_id
```

- **实体上下文注入**：`EntityContextFilter` 在 LLM 抽取前将已有实体注入 prompt，指导 LLM 使用标准实体名。若实体解析延迟到聚类阶段，新文档的抽取质量下降。
- **事件聚类依赖**：`EventClusterer` 需要 entity_id 来关联同一事件的不同 KU。延迟解析会导致聚类断裂。
- **图同步复杂度**：聚类后的实体合并需要重写已同步到 Neo4j 的节点和边，以及所有引用旧 entity_id 的 KU 和 EventCluster，工程代价显著。

**结论**：定期聚类不能替代即时解析，最多只能作为**定期修正**叠加。但修正涉及 entity_id 重映射，影响 KU、EventCluster、Graph 三层数据。

### 5.2 聚类的传递闭包放大错误

Single-linkage 聚类（常见实现方式）存在链式效应：

```
"中芯"  —0.90→ "中芯国际" —0.91→ "中微国际"
                                         ↑ 错误匹配
```

传递闭包将"中芯"和"中微国际"归为同一实体。一个错误匹配污染整个聚类。

学术界的缓解方案（correlation clustering、凝聚聚类 + 硬约束）实现复杂度显著上升，且仍需人工调参。

### 5.3 精度-召回矛盾

合并和查询对匹配器的要求相反：

| 维度 | 合并（merge） | 查询（query） |
|------|--------------|--------------|
| 目标 | 高精度：宁可漏合，不可错合 | 高召回：宁可多返回，不可漏掉 |
| 代价函数 | 错合 = 数据污染，不可逆 | 漏查 = 少返回结果，可接受 |
| 阈值倾向 | 保守 | 宽松 |

统一匹配器意味着在两个目标之间妥协：合并时太激进或查询时太保守。实际系统（如 Elasticsearch 的同义词 vs deduplication）通常将两者分开处理。

### 5.4 中文缩写的本质困难

无论用聚类还是贪心匹配，中文实体缩写是**语义问题**，不是字符串距离问题：

| 场景 | 正确判断 | 算法能做到？ |
|------|---------|------------|
| "宁德时代" ↔ "宁德" | 同一实体（缩写） | ✗ 纯字符串无法区分 |
| "小米集团" ↔ "小米" | 同一实体（缩写） | ✗ "小米"也是 2-3 字，类型推断为 Person |
| "小米金融" ↔ "小米" | **不同实体**（子公司） | ✗ 子串包含会误匹配 |
| "大吉利" ↔ "吉利" | **完全不同** | ✗ 子串包含会误匹配 |

Embedding 向量对此也不稳定——短中文名的向量空间分布密集，"小米"和"小米金融"的余弦距离可能很近。

正确处理需要别名表（gazetteer）+ 企业关系图谱（母公司/子公司），当前均不存在。

### 5.5 缺乏错误反馈和纠正机制

当前方案（无论贪心还是聚类）都是无监督的，没有人在回路中。一旦错误合并：

- aliases 被污染 → 影响后续所有匹配
- source_ku_ids 混入不属于该实体的 KU → 检索返回无关结果
- identifiers 被错误合并 → 查询指向错误实体

没有拆分机制意味着错误只能累积。定期聚类因为影响范围更大（重新分配所有 mention），出错后果更严重。

### 5.6 评估结论

| 维度 | 评估 |
|------|------|
| 与现有架构兼容性 | 差：pipeline 同步逐文档，聚类不能替代即时解析 |
| 错误控制 | 差：传递闭包放大错误，无纠正机制 |
| 匹配目标统一性 | 差：精度/召回矛盾无法消解 |
| 中文缩写问题 | 未解决：算法层面无解，需外部知识 |
| 工程代价 | 高：涉及 entity_id 重映射，三层数据变更 |
| 相比现状的收益 | 有限：核心问题（缩写、类型推断）不因聚类而改善 |

**结论**：定期聚类方案在当前系统约束下不建议采用。应保持即时贪心匹配框架，针对具体问题逐项修补。

## 6. 推荐改进方案

基于上述分析，推荐在现有贪心匹配框架内进行针对性修补。以下按优先级排序：

### 6.1 高优先级：跨语言别名加入合并流程

**改动**：在 `_find_match` 中增加跨语言别名查找逻辑，复用 `EntityRepository._CROSS_LINGUAL_ALIASES`。

**复杂度**：低（~10 行代码）
**风险**：低（仅增加匹配路径，不影响现有路径）
**解决问题**：问题一

---

### 6.2 高优先级：放宽类型硬约束

**改动**：当 normalized name 精确匹配（layer 2-3）成功时，不检查类型一致性；仅在 SequenceMatcher 模糊匹配（layer 4）时将类型作为降权信号。

**理由**：normalized name 精确匹配的置信度已经足够高，类型不一致更可能是推断错误而非不同实体。

**复杂度**：低（~5 行代码）
**风险**：低（缩小拒绝范围，不会增加误合并）
**解决问题**：问题二

---

### 6.3 中优先级：名称标准化改为单次最长匹配

**改动**：将 `normalize_entity_name` 的 `while changed` 循环改为单次扫描，选择可剥离的最长后缀进行一次剥离。

**理由**：避免过度归一化（如"控股有限公司"→"控股"→""），同时仍能处理常见后缀。

**复杂度**：低（重写 ~15 行）
**风险**：低（输出范围更保守）
**解决问题**：问题六

---

### 6.4 中优先级：加 normalized name 倒排索引

**改动**：在 `resolve_units_with_cache` 中预建 `normalized_name → entity_id` 索引，`_find_match` 优先查索引再走 SequenceMatcher。

**复杂度**：低（~10 行代码）
**风险**：无（纯性能优化，不改变匹配语义）
**解决问题**：问题三

---

### 6.5 低优先级：别名去重和上限

**改动**：追加 alias 前检查 normalized name 是否已存在；设置上限（如 20 个），超出时丢弃最早的非标准化别名。

**复杂度**：低（~10 行代码）
**风险**：低（仅限制增长，不改变匹配语义）
**解决问题**：问题五

---

## 7. 改进方案的风险与局限

上述修补方案有明确的局限性，需要架构部门知悉：

1. **中文缩写问题未解决**：子串匹配（如"宁德"↔"宁德时代"）需要别名表或企业关系图谱，不属于本轮修补范围。建议作为独立项目推进。

2. **仍无拆分机制**：错误合并一旦发生，当前无法自动纠正。建议增加实体合并审计日志（记录每次合并的 mention、匹配层级、相似度），为未来的人工审核/回滚提供数据基础。

3. **全量扫描仅优化不消除**：倒排索引加速精确匹配路径，但 SequenceMatcher 模糊匹配仍需线性扫描。在当前实体量级下可接受，未来若实体量增长到万级，需引入更高效的近似匹配方案。

4. **无跨文档实体消歧**：如果两个不同公司碰巧有相同的 normalized name（如"恒大地产"和"恒大健康" normalized 后都可能是"恒大"），当前方案会误合并。这需要 identifier 或 context 层面的消歧信号。
