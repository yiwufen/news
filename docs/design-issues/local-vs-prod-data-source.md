# 诊断教训：本地副本冒充生产真源

> 一次"看似严谨实则错误"的诊断复盘。记录根因与防护，避免在涉及远程生产数据时重蹈覆辙。
> 相关文档：`docs/SSH_TUNNEL.md`「数据真源」、`docs/design-issues/entity-merge-followup.md`。

## 一、事件

在一次图谱剪枝效果验证中，为对比传/不传 `edge_role` 的召回差异，用本地
`EntityRepository('data/news.db')` 读实体 ID，喂给远程 Neo4j 跑多跳 Cypher。

**结果**：所有实体召回全 0；进一步对比发现本地 SQLite `entity_id` 与远程 Neo4j
`Entity.id` 交集为 0（6,233 vs 23,019）。由此得出"生产环境 SQLite 与 Neo4j 主键体系
完全断裂、剪枝改造在生产失效"的结论，并判定为严重 bug。

**真相**：远程生产 SQLite 与 Neo4j **完全一致**（同名实体 `entity_id` 逐一吻合，均为
当日更新）。问题出在**对比基础**——本地 `data/news.db` 是停留在 `2026-06-22` 的旧开发
快照（约 80MB，6,233 实体），而远程生产 SQLite 已增长到 427MB / 23,020 实体。UUID 在
每次新建实体时随机生成（`src/entities.py:328` `uuid4().hex[:12]`），两份独立生成的
ID 互不重叠是必然，与系统健康无关。

## 二、根因（分四层）

### 第一层：直接技术原因

用本地文件路径（`db_path="data/news.db"`）读实体 ID，默认它代表生产数据。该默认对
"本地开发"成立，对"对比生产图谱"不成立，但**新场景沿用了旧场景的默认且未重新确认数据源**。

### 第二层：为什么错误信号没能拦下来

召回为 0 有两种可能：**图坏了，或查询起点错了**。本应是后者（输入数据源错），却被定
成前者（生产 bug）。过程中至少三个"不对劲"信号被合理化掉：

1. **首次全 0 召回被忽视**：114,810 条边明确存在却匹配不上实体，第一反应本应是"输入
   数据有问题"，却跳到"图检索失效"。
2. **"交集为 0"的极端结果反向强化错误**：交集为 0 的平凡解释是"这是两份不同的数据"，
   却选了戏剧性的"ID 体系断裂"——因为后者显得是更有价值的发现。
3. **数据量差异（6,233 vs 23,019）被套进既有假设**：把"SQLite 删了 dup、Neo4j 留了
   孤儿"的假设硬套上来，用数据**拟合**假设而非**推翻**假设。

### 第三层：认知模式根因

**从未在本 session 建立"远程生产是真源"的锚点。** SSH 隧道与 `SSH_TUNNEL.md` 是更早
session 建立的上下文；本 session 从"探索代码"起步，心智模型是"本地代码 + 本地 data
+ 远程 Neo4j（三个独立来源）"，而正确模型是"**远程 SQLite + Neo4j 是一体真源，本地
data 是其过期副本**"。

`SSH_TUNNEL.md` 写"所有服务通过 SSH 隧道访问"，"所有服务"本应提示关系库也在远程，却
被读窄成"Neo4j 和 MCP 在远程"。远程存在感弱到无法对抗"`data/news.db` 就在眼前"的
即时性强信号——**这是"遗忘"的真相：不是记忆丢失，是从未作为当前生效事实加载。**

### 第四层：系统性弱点

最危险之处在于错误**完全自洽、完全可验证、看起来极度严谨**——跑了真实 Cypher、拿到
真实数字、有表格有百分比、还和 `improvement_narrative.md` 的基准对上了。每一步单独看
都"对"，错误只埋在最底层那个未经验证的前提（本地文件=生产数据）里。

**错误的根 + 正确的推理链 = 极度自信的错误结论。** 这类错误无法靠"推理更严谨"防住，
只能靠"验证最底层前提"防住。

## 三、防护措施

### 操作层（已落地）

- `docs/SSH_TUNNEL.md` 新增「数据真源」章节，明确：本地 `data/` 是过期副本、何时必须
  用远程、同步本地的命令、对照远程前的自检清单。
- 同步本地为最新生产的标准命令固化在文档中，避免每次临时拼凑。

### 诊断纪律（需内化）

1. **遇到"全 0 / 全对不上"，先怀疑输入源，再怀疑系统。** 召回为 0 的第一假设永远是
   "我喂进去的起点错了"，而不是"图/库坏了"。
2. **跨库对比前，先证明两边是同一份数据。** 对比 SQLite 与 Neo4j 前，先各自查同一实
   体的 ID 是否一致；不一致先解决"数据源不同"，不要直接下"系统故障"结论。
3. **对极端结果（交集 0、全量失败）保持警惕，优先考虑平凡解释。** 戏剧性结论需要戏剧
   性证据；交集为 0 的第一解释是"两份不同数据"，不是"体系断裂"。
4. **验证最底层前提，而非优化推理链。** 推理链再严谨，根错了全错。每个诊断开工第一步
   确认："我用的数据/路径/服务，真的代表我想判断的那个对象吗？"

### 文档层

- 任何"远程 vs 本地"的对比结论，记录时必须附上**两边的数据时间戳与来源**，让"对比的
  是不是同一份数据"可被审阅。

## 四、验证

纠偏后直接在远程容器内查生产 SQLite，与远程 Neo4j 逐一对照：

```
英伟达    SQLite ent_fee893775071  =  Neo4j ent_fee893775071  ✓
宁德时代  SQLite ent_ee59e10de140  =  Neo4j ent_ee59e10de140  ✓
小米集团  SQLite ent_c1503049c3bf  =  Neo4j ent_c1503049c3bf  ✓
中信证券  SQLite ent_2dbd982087d6  =  Neo4j ent_2dbd982087d6  ✓
比亚迪    SQLite ent_34952f0aa61b  =  Neo4j ent_34952f0aa61b  ✓
```

生产 SQLite 与 Neo4j 主键完全一致，`entity-merge-followup.md` 记录的 6-22 prune 在生
产已生效（孤儿 0、悬挂边 0）。**之前"生产 bug"的结论不成立，予以撤销。**
